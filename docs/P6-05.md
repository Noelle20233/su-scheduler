## 1. 裁决表（D-01 … D-13）

> 每项：**规则 → 理由（对齐 P4/P5 语义与 C1–C5）→ 影响面 → 被拒替代方案**。全部**草案待批准**。

### D-01 配置模型 · 边的表达 = 扩展 `dependency=`，不新增边字段【推荐，待批准】

- **规则**：DAG 边**唯一载体** = 既有 Task v2 `dependency=` 字段，语法逐字节沿用
  dependency-schema ADR D1/D2：`[?]<task-id>[:<STATE>]`，逗号规范分隔、`DEP_MAX=32` 上限。
  「A 是 B 的链上游」⇔「B 的 `dependency=` 含一条指向 A 的 entry」。Required/Optional、
  `:STATE`（仅 `STOPPED`/`FAILED`，缺省 STOPPED）、id 字符集（`tcfg_editor_id_ok`）、
  存储层安全（`dep_validate`）、图校验（`dep_validate_graph`：未知/自依赖/环）——**全部复用，不另定义**。
- **理由**：`dependency=` 的「等待上游达期望终态」语义**就是** DAG 的入边语义；P4 已把该图做到
  registry 级无环（DFS）。链式相对 P4 的增量只有两点：「一次根触发绑定一次链运行」（D-03）与
  「下游无需自己的时间触发」（D-02 的 `trigger=chain`）。这两点都不需要改边语法。C2 复用优先；
  发明第二套边语法必然产生两套 Required/Optional、两套环检测、两处权威校验互相矛盾（违反本任务禁止事项）。
- **影响面**：零生产改动（P6-05）；P6-06 只在 `tcfg_editor_trigger_ok` 增 `chain` 族 +
  `dep_validate_graph` 口径扩展（D-08）。fixtures 可直接用现校验器验证（`tests/p6-dag` 已实跑）。
- **被拒替代方案**：
  1. **新增 `dag.edges=` 字段**：与 `dependency=` 同图双源——同一对任务可在两处声明边，
     冲突时谁权威无解；环检测须跑两遍并合并，`dep_validate_graph` 语义被分叉（违反「不得废弃
     `dependency=`、不得出现第二套不兼容语义」）；Task v2 校验矩阵（task-schema-v2）需开新键域。
  2. `dependency=` 条目加新前缀（如 `+id` 表「链内边」）：改动了 P4 冻结的 entry 文法
     （保留符号集），T1/P4 golden 面被侵入，收益仅是把「节点是否属于链」错放在边上。

### D-02 配置模型 · 链的成员标识 = 新触发族 `trigger=chain`（managed-only）；链无独立配置对象【推荐，待批准】

- **规则**：
  - **节点 = 既有 managed Task**（Task v2 文件，一文件一节点）；
  - **根 = 拥有任一既有真实触发器的任务**（boot/boot_completed/time/advanced/oneshot/delay/interval/cron，
    Trigger Schema v2 D41 家族全集）；根**不需要**任何新字段；
  - **链内非根节点 = `trigger=chain`**：无自主时间触发，**仅**由链传播释放执行（D-04）。
    `chain` 是 trigger 家族的**裸关键字**（同 `boot_completed` 先例，无参数）；
  - 链**不是**配置对象：无 `chain.id=`、无 chain 注册表、无 chain 专用 IPC op、无第二循环。
    链的身份即其根（D-03）。
- **理由**：「下游不定时、只被链点火」在既有模型里唯一自然表达就是 trigger 家族（P5-04 先例：
  新家族只进 managed、`tcfg_editor_trigger_ok` 白名单扩展、legacy 解析零触碰=B16）。
  独立链配置对象需要新存储实体+新校验面+新 IPC 面（B7 违例风险），而根 id 已经提供全局唯一、
  已过 `secv_id_ok` 的身份。一个 Task 只属一条链的链归属歧义（同节点被两个根依赖）：允许
  ——共享节点是 DAG 常态，两链各自独立计 run（节点态按 run 记录，互不串扰；D-09）。
- **影响面**：P6-06：`tcfg_editor_trigger_ok` 增 `chain`；`trigger_decide` 增 `chain` 分支
  （缺省 `due=N`，由链引擎按 frontier 释放）；`legacy_adapter_parse` **不动**（legacy 行不可能
  派生 `trigger=chain`）。Editor schema `task-editor-schema.md` 增枚举（追加）。
- **被拒替代方案**：`chain=root-id` 新字段标成员（第二身份源，与边集合可矛盾——字段说属于链 A、
  边却说链 B 可达它）；为链建独立 `.chain` 文件对象（新权威实体，import/export/回滚/原子写全套
  扩容，P0-P5 六处版本一致性面被波及，成本远超收益）。

### D-03 触发一次后是否允许重复执行 = 允许；每轮根触发恰好生成「一次链运行」，run 绑定 cycle token【推荐，待批准】

- **规则**：链是**模板**；每次根触发 = 创建一次链运行（chain run）。根触发器为周期族
  （`interval:`/`cron:`/分钟精确/advanced/boot/boot_completed）时链随之重复运行。
  - **run 身份**：`chain_id = 根任务 id`（字符集天然过 `secv_id_ok`）；
    `run_id = sched_cycle_token`（`YYYYMMDDHHMM`，12 位数字 ⊂ id 字符集，与 P6-02 跳拍补偿同一时间轴）；
    存储路径 `$base/dag/<chain_id>/runs/<run_id>/`。
  - **同窗口至多一次**：run 目录名=token，一次 `mkdir`/原子写即去重——同一根同一分钟窗口至多一次
    链运行，对齐任务级 `sched_cycle_seen/mark` 与 P6-02 catch-up 的「同窗口至多一次」原则。
  - 链运行**登记时机** = 根动作**终态被观察到**（执行通道覆盖 `sched_execute_one`、
    `sched_advance_waiting` 释放、P6-02 catch-up、`scheduler_boot`；具体观察机制归 P6-06，见 ADR 未决 U-1）。
  - **手动 `tctl start/restart <根>` 不创建 run**（v1）：run 是调度器行为产物；手动执行保持 P4 D17
    既有语义（跳门控、单任务执行），不隐式点火整链。
- **理由**：「触发一次后是否允许重复执行」的答案由触发器家族自然决定，无须新策略位；token 派生
  零新 ID 发明（任务书「链运行 ID 派生对齐 sanitize 字符集」直接满足，12 位数字最严）。
  boot 根经 `scheduler_boot` 点火（每次开机一轮），与 boot 任务既有语义一致。
- **影响面**：P6-06 新增 `$base/dag/` 目录树（run.txt，见 ADR §4）与登记扫描。
- **被拒替代方案**：`<root>_<epoch秒>` run id（秒级不可测且同分钟可双 run，破坏「同窗口一次」）；
  哈希链 run id（`<root>_<hash(token)>`——不可读、目录爆炸，无对应收益）；「根触发后链仅运行一次」
  （interval/cron 根的例行编排场景直接报废，违背立项动机）。

### D-04 执行编排 · 拓扑序 / 并行 / 串行【推荐，待批准】

- **规则**：
  - **frontier 判定**（每 tick 对每个活跃 run 一次）：节点 N（`trigger=chain`）可执行 ⇔
    本 run 内 N 的**全部 Required 入边上游**均已达各自 entry 指定期望终态
    （缺省 `STOPPED`，含 `:FAILED`）且 N 在本 run 内**尚无终态**（单尝试语义，重试归 D-06 节点级）。
    Optional（`?`）入边不阻塞（D-05 表）。
  - **串行 = 边的自然序**；**同层并行**：一个 run 内处于 STARTING/RUNNING/HEALTHY/UNHEALTHY/
    RECOVERING 的节点进程数 **≤ `DAG_PARALLEL_MAX=4`**，超限的已释放节点顺延至下一 tick。
  - **无每任务新执行体**（对齐 P2-12 原则）：并行度只是「本 tick 是否再 spawn」的门；节点进程
    仍是既有 `action_run` → `execute_task` 后台进程模型。链引擎零常驻、零子 shell 长驻。
  - 节点自身 P4 门控/条件**不裁剪**：释放判定叠加 `sched_cond_check`（condition 假 → 本 tick 不
    释放，节点留 PENDING，审计 `dag=cond-unmet`；链无窗口概念，不适用「rearm 跳过」路径）。
- **理由**：frontier 与 P4 `sched_dep_satisfied` 的判定材料完全同源（dependency entry + 上游
  实时态），只是「上游终态须落在**本 run 的登记簿**上」这一 run 绑定差异——这正是 `run.txt`
  存在的全部理由（state.txt 无法区分上游的哪次执行属于本 run）。
- **影响面**：P6-06 引擎 pass（`scheduler_tick` 内、advance 通道之后、主循环之前）。
- **被拒替代方案**：事件推送（上游收尾回调直接拉起下游）——需要改 `execute_task`/`action_run`
  收尾路径（C2 违例）且丢失 tick 幂等恢复性（daemon 重启即断链）；「同层全并行无上限」——
  一条链一 tick 可 fork 32 进程，Android 低内存设备不可接受。

### D-05 失败传播 = 与 P4 D15/D16 一一对应，不新增第二套语义【推荐，待批准】

- **规则**（边 → 节点 → run 映射表；「期望终态」= entry `:STATE`，缺省 STOPPED）：

| 上游在本 run 的终态 | 边 entry | 本节点行为 | 对 run 的影响 | 既有语义锚点 |
| :-- | :-- | :-- | :-- | :-- |
| = 期望（含 `:FAILED` 且上游 FAILED） | Required | 满足 → frontier 释放 | — | D15 行 1 |
| ≠ 期望（如上游 FAILED，缺省边） | Required | **立即 FAILED**（不等超时；经 `gate_fail` 事件，P4 通道） | 无 Required 可行动作且无在途 → run=FAILED | D15 行 2 |
| 未终态 / 已删除（dep missing）/ DISABLED | Required | 有界等待（run 时限 D-10）→ 超时 FAILED | 同上（超时后） | D15 行 3-5 |
| 任何不满足 | Optional（`?`） | **不阻断**，记 `opt-unsat`（DAG 语境含上游 FAILED） | run 结论按其余节点计 | D16 |
| 节点 DISABLED（链中断路） | （任意出边） | 该节点永不执行 → 其 Required 下游走「非终态等待→超时 FAILED」 | 级联同上 | D15 |

  - 传播**沿边级联**：上游 FAILED 使下游 FAILED，下游的下游按同表继续（frontier 每 tick 天然收敛）；
  - 上游 FAILED + 出边 `:FAILED` = **满足**（故障处置分支合法表达，D15 原文复用）；
  - 全部节点终态后：无 FAILED 节点 → run=SUCCESS；否则 run=FAILED；结果**只写 run.txt**（D-13）。
- **理由**：任务书第 4 条硬性要求「一一映射、不得出现第二套不兼容语义」。上表逐行取自 D15 矩阵 +
  D16，仅把「按触发窗口复查」换成「按 run 登记簿复查」——判定函数 P6-06 可与 `sched_dep_satisfied`
  共享实现。
- **影响面**：零（裁决层）；P6-06 引擎与 `gate_fail` 事件复用。
- **被拒替代方案**：链级「快速失败」策略位（fail-fast 杀整 run 在途节点）——杀进程改执行路径
  （C2），且与「节点重试仅节点级」（D-06）打架；新增边类型 `--abort-chain`——第二套边语义（D-01）。

### D-06 优先级矩阵 = 既有链路插一层，Retry 仅节点级、不自动重放整链【推荐，待批准】

- **规则**（每 tick 单循环内固定序）：

```
 根侧：trigger_decide(既有 D44 序) ──due──▶ sched_gate_check(P4 依赖) ─▶ cond(P4) ─▶ action_run
 链登记：观察到根本轮终态 ─▶ 创建/更新 run.txt（token 去重）
 节点侧（每活跃 run）：edge frontier(D-04) ─▶ cond(sched_cond_check) ─▶ 并行闸(≤4) ─▶ action_run(既有)
 每 tick 固定层序：WAITING advance(P4) ▶ 链引擎 pass(新，P6-06) ▶ retry-arm(P4-07) ▶ catch-up(P6-02) ▶ 主循环
```

  - **Retry**：节点 FAILED 仅按**该节点自身** `retry.max/interval/cooldown`（P4-07 原语义）节点级
    退避重试（run.txt 记录该节点 attempt 计数由 retry.count 既有工件承载）；**链永不自动整链重放**；
    重试成功 → 节点终态更新入 run.txt → frontier 前进。gate_fail 类（依赖失败传播）**不接退避**
    （D25 原文沿用：传播失败 ≠ 进程崩溃）。
  - **Cooldown / 进程级 Crash guard / Recovery(supervisor)**：全部**节点级不变**；D25 协同
    （gate.fail 标记 → 不 auto-recovery）对链传播失败同样成立。
  - **跳拍补偿（P6-02）**：补偿只作用于**根**的触发窗口（可补偿族 = `sched_compensable` 原集）；
    补执行根成功 → 照常登记 run；链内节点不参与独立补偿（其时间轴就是 run）。
  - **condition 假（根侧）**：根本轮不执行 → 无 run（触发从未发生）。**条件假（节点侧）**：见 D-04。
- **理由**：整链自动重放会重复执行已成功的副作用节点（幂等无法静态判定），Android shell 任务尤其
  危险；节点级重试 + 人工/下轮根触发重放，语义封闭。链 pass 放在 advance 之后、retry-arm 之前，
  保证「本轮新释放节点」与「本轮退避接线」互不踩脚（与 P4-07 D24 的退避优先原则一致）。
- **影响面**：P6-06 接线序；既有五段路径零改动。
- **被拒替代方案**：链级 `retry.policy=chain`（整链重放）——上列重复副作用风险 + 需新配置维度；
  链 pass 置于主循环之后——同 tick 内节点被执行两次的竞态窗口。

### D-07 手动控制 = 节点级 only（tctl 19-op 复用）；disable=链中路断【推荐，待批准】

- **规则**：
  - `task stop/restart/start/check <节点>`（含 P5-07 批量 ≤50）逐节点生效，**链零特判**：
    - 节点被 stop → STOPPED = 缺省期望终态 → **其下游按 D-05 正常释放**（与 P4「手动停止即成功
      语义」一致，文档化为有意行为：需要「停止=失败」时用显式边 `:FAILED` 或 disable 断路）；
    - 节点 restart（force start）→ 该节点单点重执行，其终态更新入**当前活跃 run** 的登记簿；
    - stop 根 → 仅根进程；活跃 run 继续（除非根终态使 Required 边不满足——STOPPED 满足缺省边，
      故通常继续）。
  - **disable 节点**（`enabled=0`）→ 该节点不可执行（DISABLED 非满足依据，P4 D15 原文）→ 其
    Required 下游「dep disabled 有界等待 → run 超时 FAILED」= **中断路**。这是文档化行为，不是 bug。
  - **v1 无链级取消/暂停原子操作**：run.txt 的 `CANCELLED` 枚举**预留不产出**（诚实声明）；
    需要「停链」= 批量 disable 链内节点（既有 CLI）。
  - 零新 IPC op（B7）；`task-config`/CLI 对 `trigger=chain` 无特判（校验统一走 editor 路径）。
- **理由**：tctl 语义在 P2-07/P4 D17 已冻结到 183 迁移级；任何「链级 stop 级联杀进程」都要改
  stop 路径并触发 supervisor 交互，风险不对称。中断路用 D15 既有「有界等待→FAILED」表达，
  零新状态。
- **影响面**：零生产改动；文档（README/help）在 P6-06 一并说明。
- **被拒替代方案**：`task stop-chain <root>`（新 CLI→级联 stop=新执行语义+批量竞态）；IPC
  `CANCEL_DAG` 新 op（B7 违例）。

### D-08 配置期校验 = `dep_validate_graph` 口径**升级**（既有消息零变化 + 新增链规则）【推荐，待批准】

- **规则**（P6-06 实现；写路径/导入/快照沿用 D9 接入点）：
  1. **继承不改动**：未知依赖/自依赖/环检测的消息文案、rc、覆盖节点（`<id> <content>`）协议
     逐字节保持（P4 golden + `tests/p6-dag` 已锁定基线）；
  2. **新增链规则**（全部**配置期拒绝**，消息前缀沿用 `[task-config] ERROR:`/`[editor] ERROR:`）：
     - `chain depth <n> exceeds DAG_CHAIN_DEPTH_MAX=16`（任一链闭包最长路；`cycle` 拒绝在先，
       故最长路必存在、可算）；
     - `chain nodes <n> exceeds DAG_CHAIN_NODES_MAX=32`（自根闭包节点数）；
     - `chain edges <n> exceeds DAG_CHAIN_EDGES_MAX=128`（闭包内去重边数，含 Optional）；
     - `chain node without incoming edge '<id>'`（`trigger=chain` 但 dependency 无有效 entry =
       孤儿，永不可达）；
     - `chain root '<id>' has incoming chain edge`（根自身 `trigger=chain` 却又是他链闭包节点
       之外的矛盾形态不需要——根=有真触发器，天然无此歧义；此条**不设**）。
  3. **校验域** = 对「替换后有效集合」逐根求闭包（闭包按依赖反向可达 `trigger=chain` 节点），
     复杂度 O(V+E)，V≤registry 规模（toybox 可承受，见 D-10 上限互锁）。
- **理由**：环已在配置期拒（D7），链的上限/孤儿属同类「结构非法」——配置期拒绝优于运行期
  半执行；复用同一函数同一接入点，editor/import/apply/set 四写路径自动全覆盖（D9 表原文）。
- **影响面**：P6-06 在 `dep_validate_graph` 尾部增链段（前置结果零回退：非链任务文件组合
  行为逐字节不变——`tests/p4-dependency` + `tests/p6-dag` 双侧守卫）。
- **被拒替代方案**：新函数 `dag_validate_graph` 独立入口（四写路径逐个接线，遗漏面×4）；
  运行期才发现超限（半途断链，产生孤儿 WAITING）。

### D-09 运行期图变更 / 节点删除 / 回滚一致性【推荐，待批准】

- **规则**：
  - **run 成员集**在登记时冻结（run.txt 头部 `root:` + 当时闭包节点列表）；
  - **frontier 每 tick 按「当前图 + 成员集」重算**：改边 → 立即生效（新边须仍过 D-08——
    写路径拒绝环/超限，故重算必终止）；成员集外新节点**不加入**进行中 run；
  - **节点删除/禁用（运行中）**：REQUIRED 入边视同 dep missing/disabled → 有界等待 → run 超时
    FAILED（D-05 表行 3）；该节点自身在 run.txt 保持最后登记态；
  - **配置回滚/B9**：DAG 声明是 Task 文件（配置域），原子写/回滚语义零变化；`$base/dag/` 是
    **运行态数据**（同 `tasks/`、`schedule_state.txt` 域）——回滚配置**不回滚** run.txt（数据面
    前滚原则）；run.txt 损坏/半写 → 引擎视 run 为不可解析 → 记审计 `dag=run-corrupt` 后按
    超时路径收敛 FAILED 并被 prune（不做二次猜态）；
  - **tmp+mv 原子写** + `secv_sweep_tmp` 扩展纳入 `$base/dag/*/runs/*/run.txt.tmp.*` 兜底
    （P6-06 改动清单点名）。
- **理由**：成员冻结防「图变更凭空扩 run」；边每 tick 重算防「run 卡死在已删边」——两者合起来
  给出可测试的一致性边界。运行态不随配置回滚与 P3 既有「tasks/ 不随 import 清空」一致。
- **影响面**：P6-06（run.txt 读写 + sweep 一行扩展 + `secv_fix_perms` 覆盖 `$base/dag` 0700）。
- **被拒替代方案**：登记时快照整图进 run（边不可变——用户改边后老 run 照旧图跑，语义反直觉）；
  运行中禁止图变更（配置写路径加链活跃锁 = 新失败模式与死锁面）。

### D-10 上限数值与超限行为【推荐，待批准——人工重点审数值】

| 上限 | 值 | 理由 | 超限行为 |
| :-- | :-- | :-- | :-- |
| `DAG_CHAIN_NODES_MAX`（单链闭包节点） | **32** | 与 `DEP_MAX=32` 同形；一 run.txt ≤ ~64 行，单遍 awk/tick 在 toybox ~ms 级 | 配置期拒绝（D-08） |
| `DAG_CHAIN_EDGES_MAX`（单链闭包去重边） | **128** | 32 节点平均出度 4；frontier 单 tick O(V+E)≤160 次字符串比对 | 配置期拒绝 |
| `DAG_CHAIN_DEPTH_MAX`（链最长路） | **16** | 病态长梯的等待放大 = 深度×节点耗时；16 远超实用链且使 `run 超时` 前扫描成本可忽略 | 配置期拒绝 |
| `DAG_RUNS_MAX`（全 scheduler 活跃 run 并发） | **8** | 8 run × 32 节点 ≈ 每 tick 256 次 state.txt 读，tick 预算内；防「一键导入造出千链」资源风暴 | **运行期不启动新 run**（审计 `dag=run-limit`），根与既有任务照常执行，不杀在途 |
| `DAG_PARALLEL_MAX`（单 run 在途节点进程） | **4** | Android 单链 ≤4 并发进程；对齐 P2-12（只限 spawn 数，无线程/池） | 超限释放节点**顺延下一 tick**（不丢弃） |
| `DAG_RUN_TIMEOUT`（单 run 总时限） | **86400 s** | 对齐 `WAIT_MAX`（P4-05/07 语义轴一致：超 1 天未收敛即死局） | run=FAILED（`run-timeout`），frontier 停止释放；**在途节点进程不强杀**（其生死仍归节点级 timeout/supervisor） |
| `DAG_RUNS_KEEP`（每链历史 run 目录） | **8** | 同 `TASK_DIRS_MAX` 修剪哲学；观测窗口 ≈ 根触发周期×8 | 最旧目录 prune（tmp+mv 域，含 `.tmp.*` sweep） |

- 常量全部 `VAR=${VAR:-默认}` 环境可覆盖（测试确定性，先例 `WAIT_MAX`/`DEP_MAX`）。
- 孤儿链节点/超边等**结构性**问题一律配置期拒绝；**规模性**并发超限一律运行期拒启动——
  原则：错配置不让写盘，资源风暴不误杀用户任务。
- **被拒替代方案**：无上限（D35 对 WAITING 的论证不适用——run 数由根周期×链长决定，可无界增长）；
  超限杀在途 run（副作用任务被链超时腰斩 = 数据损坏风险，违背节点执行路径不变的 C2）。

### D-11 跨任务自动触发 = 仅沿声明边传播，禁止任意目标触发【推荐，待批准】

- **规则**：链引擎可「触发」的目标集合 = 该 run 成员集内、由 `dependency=` 边指向的
  `trigger=chain` 节点，**再无其他**。不提供任何「按名点火他任务」的引擎入口（无新 IPC op、
  无 CLI `dag-run <id>` 之类 v1 API）；节点 action 内容仍由用户在 Task 文件中声明，执行路径
  （SYSTEM/TERMUX/INTERACTIVE → `action_run` → `execute_task`）**零改动**——链改变的只是
  *何时允许执行*，不改变*执行什么、怎么执行*。任务正文里用户自行调 `su-scheduler task start`
  属既有 CLI 能力（Root 域），不由 DAG 机制提供、不在本裁决扩张/收紧范围（诚实划界）。
- **理由**：任务书第 9 条原文裁决；「节点=既有 Task + 执行路径不变」是 C2 的最小安全面。
- **影响面**：零（裁决层）。
- **被拒替代方案**：`chain.fire=<id>` 动作扩展（任意目标=注入面与环外环）；引擎暴露 `RUN_CHAIN`
  op（B7 违例 + WebUI Root 直执链风险）。

### D-12 Legacy 零关系声明（B16 先例）【推荐，待批准】

- **规则**：DAG/链**仅 Managed（Task v2）**。Legacy `config.txt` 语法零变化（C4）：无 `chain`
  触发族、无链 modifiers；`legacy_adapter_parse`/`parse_modifiers`/`extract_command` 零 diff；
  legacy 行导入永不产生 `trigger=chain` 任务。`tests/legacy/golden.sh`（8/0）与 `tests/parsing`
  golden 持续为守卫。managed 关闭（回 legacy 模式）时 `$base/dag/` 存量目录**闲置不读**（引擎
  pass 仅 managed 模式运行）。
- **理由**：B16/P5 新家族同款边界；legacy 域任何扩展都威胁 P0 冻结的解析 golden。
- **影响面**：零。
- **被拒替代方案**：legacy 行加 `; : --chain` modifier（C4 违例，直接拒）。

### D-13 链级状态 = 文件级新记录；183 条迁移零修改【推荐，待批准】

- **规则**：
  - 任务状态枚举**不扩充**：节点态 ∈ 既有 11 态（`state.txt`，TSM 183 迁移管辖，零增删改）；
  - 链运行态 ∈ `run.txt` 的 `state=` 字段，**新命名空间**、文件级记录：
    `PENDING`（已登记，无节点在途）→ `RUNNING`（有节点在途）→ 终态 `SUCCESS` / `FAILED`；
    `CANCELLED` 枚举**预留，v1 不产出**（D-07）；
  - 节点↔链映射：节点达到其边期望终态 = run.txt 行满足；节点 FAILED（执行失败或传播）→ 记
    `FAILED` 并可能级联（D-05）；run 终态判定见 D-05 末条；
  - 事件令牌新增仅两类，全部走 `RT_EVENTS`（D13 先例，**不入** `TSM_CAUSES`）：
    `dag_register`（run 创建）、`dag_dispatch`（节点释放）；既有 `gate_wait/gate_ok/gate_fail/
    rearm` 令牌语义不变（链节点若借道 WAITING 通道，事件即 P4 原令牌）。
- **理由**：run 是跨任务的聚合记录，天然是「文件」而非「状态机状态」；183 迁移是 P2-07 出口
  冻结（`tests/state-machine` 25→183 断言），任何扩充即回退。
- **影响面**：零（裁决层）；P6-06 只写 run.txt + 2 个事件令牌。
- **被拒替代方案**：任务枚举加 `CHAINED` 态（183 表全量重审 + WebUI counts 键语义破坏 B8）。
