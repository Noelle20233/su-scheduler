## 2. 设计决策

### 2.1 next_due 真计算（最大缺口）

现仅 `tpr_trigger_time_next_due`（返回**距下次秒数**）。为 6 个 Provider 补齐，**统一语义 = 距下次命中的秒数**（与 time 一致，避免破坏 providers 套件 L101-108 断言）：

| Provider | next_due 计算 |
| :-- | :-- |
| advanced（weekly/nweekly/monthly/nmonthly/yearly） | 计算距下次匹配的秒数（当前时间 + 逐周期推进找首个匹配窗口）；复杂度可控（分钟/日推进，≤ 366 天上限防死循环） |
| bootcompleted | 上下文=1 → 0；否则无法预测 → 返回失败（无确定性下次时间） |
| oneshot | 距 `oneshot:HHMM` 的秒数（当天或明天，取最小正值） |
| delay | `dl_<tid>` 基准 + N 分钟 → 距基准+N 的秒数（基准缺失 → 无法预测失败） |
| interval | `iv_<tid>` last-run + N 分钟 → 距 last+N 的秒数（last 缺失 → 无法预测失败） |
| cron | 5 段全字段推进找下次匹配的秒数（分钟级推进，≤ 一年上限） |

> **简化裁决**：next_due 是"预计"信息，允许对复杂族（advanced/cron）做**分钟级近似**（不追求跨月/闰年精确），上限防死循环。oneshot/time/cron 有精确到分钟的秒数；delay/interval 基于 last-run 状态；bootcompleted/boot 无确定性下次（返回失败，CLI 显示 `next_due=` 空）。

### 2.2 触发原因透传入审计

- `trigger_decide` 已输出 `cause=`（time_trigger/advanced/oneshot/cron/interval/delay/boot_completed/manual_exec/boot）。
- `sched_execute_one` 解析 due 后**透传 cause** 到 `op=exec` 审计行（追加 `cause=$cause`）。
- `sched_advance_waiting` 的 `op=advance|action=start` 同样透传（该路径也调 trigger_decide）。
- **只增审计字段，不改既有字段**（D32）。

### 2.3 task_cli_status 新字段（task status）

追加（均为新 key=value 行，既有行零改动）：
- `trigger_kind=`：`tpr_trigger_<family>_parse` 输出（`kind=...;...`），经 trigger 串映射家族后调用 parse
- `next_due=`：Provider next_due 结果（距下次秒数，空=不可预测）
- `last_trigger_cause=`：最近一次 `op=exec` 审计行的 `cause=`（读 scheduler/audit.log 反向 grep task id，取末行）
- `condition_state=`：`obs_cond_state` 摘要（ok/unsat/illegal/空=恒真 ok）
- `dependency_state=`：`obs_dep_state` 摘要（ok/satisfied/waiting/unsat）
- `Gate:` 保持仅 WAITING 输出（既有行为不变）

### 2.4 task-info 新字段（managed 域附加行）

在 P4-09 `Dependency:`/`Condition:` 块后追加（仅 RUNTIME_LOADED=1 && managed）：
- `Trigger: kind=...;...`（parse 结果）
- `Next Due: <秒数>s` 或 `Next Due: -`（不可预测）
- `Last Trigger Cause: <cause>`
- `Condition State: ok/unsat/illegal`
- `Dependency State: ok/satisfied/waiting/unsat`

### 2.5 CLI 批量查询

- `task status <id> [<id>...]`：CLI 层循环 `task_cli_status_id`（registry 直读，无 IPC），逐任务输出 + 聚合退出码（仿 P5-07 `task_ctl_multi`）。
- 单 id 行为与既有完全一致。

### 2.6 审计文件分裂（不做合并）

- `scheduler/audit.log`（sched_audit）与 `audit/audit.log`（legacy cmd_audit）保持两文件。
- P5-08 的 `last_trigger_cause` 从 `scheduler/audit.log` 反向 grep（只读），不新增 CLI 命令读整个调度审计（避免 scope 膨胀）；如需完整调度审计展示，登记 P5-09/后续。
