## 2. 裁决落地（ADR 摘要，详见 dependency-schema.md §13）

- **D30 可观测面复用既有 IPC 只读通道（不新增 op）**：依赖/条件/门控状态全部经
  `GET_TASK_DETAIL` / `GET_SUMMARY` / `GET_TASK_EVENTS` 暴露——`dependency_state`
  复用 §20 `sched_dep_satisfied` 只读消费（返回码 0/1/2 → satisfied/waiting/unsat，
  无副作用），`gate_state` 由 `obs_gate_state` 读运行目录 state.txt + events.log
  最新 gate 事件/工件（retry.until / gate.fail）得到。CLI 侧 `task status` 经既有
  `task_cli_status_id` 通道补 dependency=/Gate 行；`task-info` 经既有旧工件命令
  附加 managed 字段。**不加新 IPC op**（白名单仍 19 op，B7）。
- **D31 JSON 只增键不删改（B8 统一契约）**：GET_TASK_DETAIL task 对象既有字段
  （id/name/status/trigger/action/enabled/health/recovery/pid/last_*/restart_count/
  run_count/source/has_run_dir）**名字与结构零变更**，仅新增 4 键；GET_SUMMARY
  counts 既有 7 键不变，仅新增 `"waiting"`。WebUI 前端对未知键的既有容错
  （`counts.total || 0` 等）自动兼容新键，无需前端改动。
- **D32 CLI 旧输出兼容**：task status / task-info 既有行格式**不动**（新行附加）；
  `dependency=`/`condition=` 空值输出空；legacy 域 task-info **不显示新字段**
  （managed 才显示）；`Gate:` 行仅 WAITING 时输出（缺省空），非 WAITING 不产生
  额外行。task-output / task-log 语义零改动。
- **D33 WAITING 控制行为固化（引用 P4-05 D17）**：WAITING 下 start/stop/restart/
  check 行为 **不再改动实现**，本文档与测试固化：force start（含 restart）跳过
  门控直接执行、非 force start 拒绝（rc 3）、stop 不写状态、check 只健康探测不改
  state.txt；相应查询面（GET_TASK_EVENTS 的 gate_wait/gate_ok/gate_fail/retry
  事件原因）作为可观测证据。
