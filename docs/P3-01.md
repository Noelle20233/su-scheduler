## 4. 任务 2/3：加载关系与「legacy 调度仍为实际执行入口」

### 4.1 Runtime 库 / daemon / CLI 加载关系

三个生产模块共用**同一加载契约**（daemon 与 CLI 头部同表达式，P2-02 §4）：

```
RUNTIME_LIB="/system/bin/su-scheduler-runtime"     # 唯一生产 runtime lib
. "$RUNTIME_LIB" 2>/dev/null && RUNTIME_LOADED=1 || RUNTIME_LOADED=0
runtime_lib_selfcheck >/dev/null 2>&1 || RUNTIME_LOADED=0
```

| 模块 | 加载 | 失败 fallback |
| :-- | :-- | :-- |
| `su-schedulerd`（daemon） | 头部加载 + selfcheck；启动记一条 INFO/WARNING | legacy 模式继续（不中断、不重试） |
| `su-scheduler`（CLI） | 头部加载 + selfcheck；`task` 子命令 `RUNTIME_LOADED` 门控 | 旧 CLI 命令零改动、零输出噪音 |
| `su-scheduler-runtime`（库） | 单文件自包含（§1→§18 按依赖序），零外部 source | 路径隔离门禁（`tests/runtime-lib` 断言） |

库版本：`RUNTIME_LIB_VERSION="1.12.0"`（P2-14 收口）。selfcheck 校验 40+ 个
生产函数存在性（见库尾 `runtime_lib_selfcheck`）。

### 4.2 legacy 调度仍是实际执行入口（确认）

- daemon **主循环 `while true`** 仍逐行扫描 `config.txt`（FD3），用既有
  `parse_modifiers` / `extract_command` / heredoc 重建 / `should_run_advanced_schedule`
  做 boot / time / advanced 触发判定——**触发决策的实际执行者未变**。
- 执行点：boot（启动段）、`--run-once-now`、advanced、time 四处，均以
  `RUNTIME_LOADED` 门控旁路 `action_run`，`else` 分支 `execute_task` **原样保留**
  （P2-06 委托既有 7 参执行器，不建第二执行器）。
- 新 Runtime 层（registry / idmap / trigger_decide / state / supervisor /
  protect / shadow）全部是**旁路叠加**：shadow 只镜像比对不消耗扫描结果；
  supervisor 每 tick 对 registry 中的受监督任务至多一步；state 双写为**新事实源**
  但旧工件 status/pid/output/exit_code 只读不动——**legacy 调度路径逐字节兼容**。
- 证据：`tests/legacy/golden.sh`、`tests/legacy/delete-pipeline.sh`、
  `tests/cli/test.sh`、`tests/legacy-adapter/test.sh` 全绿（1215 PASS 内）。

**结论**：P3 阶段任何 WebUI / 配置改造必须继续以「legacy 调度为执行入口 +
Runtime 旁路为数据面」为不变量（P3-ARCHITECTURE-DECISIONS §4 已冻结）。

## 5. 任务 4：模块版本与 Runtime 版本的映射规则

| 版本面 | 位置 | 值 | 校验 |
| :-- | :-- | :-- | :-- |
| 模块版本（用户可见） | `module.prop` version / versionCode | `v1.6.8` / `11608` | build_check（8 处一致） |
| 模块版本（单一事实源） | `build.sh` VERSION | `v1.6.8` | build_check |
| CLI / daemon VERSION | `su-scheduler` `su-schedulerd` | `1.6.8` | build_check |
| README badge / update.json | version/versionCode/downloadURL/changelog | `v1.6.8` / `11608` | build_check |
| 文档头 | `.su-scheduler-docs` / README 头部 | `1.6.8` | build_check（Q12 扩展） |
| **Runtime 库版本（内部实现线）** | `su-scheduler-runtime` `RUNTIME_LIB_VERSION` | **`1.12.0`** | 独立于 8 处模块校验；仅 selfcheck 存在性 |

**映射规则**：
1. **模块版本 `v1.6.8` 是发布契约**——module.prop / build.sh / 两 bin /
   README / update.json / 文档头共 8 处必须逐字节一致（`tests/p1-build/build_check.sh`
   强制）；版本变化走 `bump_version.sh`。
2. **Runtime 库版本 `RUNTIME_LIB_VERSION` 是内部实现线**——随 P2 每个特性步
   递增（v1.0.0 → 1.12.0），表示生产库内含 § 功能集合；**不与模块版本绑定**，
   不参与 8 处模块一致性校验（它描述"库里有什么"，不是"发版号"）。
3. 模块发布 `v1.6.8` 打包 `runtime v1.12.0`——若库 API/§ 集合有破坏性变化，
   模块版本必须同步大版本；若仅新增 §（向后兼容叠加），模块可维持版本（P2 实践）。
4. CI 校验面：模块 8 处（build_check）+ 库 selfcheck（存在性）。**缺口登记**：
   `RUNTIME_LIB_VERSION` 尚未纳入 build_check 的版本一致性断言（低风险——库自包含、
   打包经 zip 成员校验，且 selfcheck 已拦缺失；见决策文档 §5 风险项 R4）。

## 8. 任务 7：Registry 初始化是否必须移动到单实例锁之后（审计）

### 8.1 现状（daemon 启动序列关键段）

```
L55-67  加载 runtime lib（RUNTIME_LOADED + selfcheck）
L74-81  crash_guard_enter（降级/节流 → 快速退出 rc2/3）
L85-94  shadow_init → registry_init（建快照+current 指针）
        runtime_map_refresh / lifecycle_startup_registry / trigger_decide 预热
…
L592-611 单实例保护（等待旧 daemon 退出，最多 5×1s）
L613-622 僵尸剪枝（旧 status.txt=RUNNING → ZOMBIE_CRASHED）
L631-634 runtime_scan_stale + state_rehydrate_residual
L637    echo $$ > LOCK_FILE        ← 单实例锁在此才声明
L642+   boot 任务 → 主循环
```

### 8.2 审计结论

**Registry 初始化（shadow_init/registry_init/lifecycle_startup_registry）当前
位于单实例锁声明（L637）之前、单实例等待（L592）之前。** 正常单实例运行下无
问题；**restart 重叠窗口**（旧 daemon 尚未完全退出时新 daemon 已进入启动段）
存在**理论竞态**：新旧两实例可能并发写 registry（snapshot 序号 `snap_<N>` 确定
性递增 + `current` 指针原子 tmp+mv 切换），最坏 last-writer-wins，不损坏旧工件、
不影响 legacy 执行（registry 是旁路数据面）。

**是否必须移动**：
- **不构成 P3-01 阻断**——registry 是只读旁路/镜像层，写入原子化 + KEPT 回退
  兜底，`tests/shadow`、`tests/lifecycle-prod`、`tests/p2-integration` 全绿；
- **推荐移动**——把 L85-94 的 registry 初始化整体移到 **L637 之后**（锁声明
  后、boot 任务前），可彻底消除 restart 重叠写竞态，且语义更贴近「先拿单实例锁、
  再初始化数据面」。这属于 daemon 调度路径外的启动顺序调整，**P3-01 禁止改
  daemon**，故登记为决策与风险项（决策文档 §4 决策 D1 / 风险 R2），由 P3-02+
  或专门接线任务实施（改后必须跑全量回归 + 设备冒烟）。
