## 2. 设计（受控通信链）

```
WebUI（浏览器侧，未来阶段）
    │  只调本地客户端（su-scheduler ipc <OP> ...）
    ▼
validated IPC（请求/响应文件通道，$DATA_DIR/ipc/，chmod 700）
    ▼
su-schedulerd（ipc_server_poll 逐秒非阻塞轮询 → ipc_dispatch → op handler）
    ▼
validated Task operation（仅 START/STOP/RESTART 落 action_run/supervisor_stop_task）
    ▼
Root action
```

**禁止出现**：WebUI JavaScript 直接执行 shell / 直接把任意 shell 字符串当作控制
指令传进 daemon。本层以「值一律 base64 + 参数键白名单 + 12 op 白名单 + 固定请求
格式 + 长度受限 + 每请求唯一 ID + 0700 权限 + 原子响应文件」实施。

### 2.1 传输选型（ADR D1）

- **采用**：`$DATA_DIR/ipc/`（chmod 700，root-only）下的**请求文件 + 响应文件**
  通道（客户端原子写 `<req_id>.req` → daemon 逐秒轮询处理 → 原子写回
  `<req_id>.resp`）。
- **不采用 FIFO 的理由**：POSIX sh 无法便携地做**非阻塞** FIFO 读取（`read` 对
  空 FIFO 阻塞；需要 O_NONBLOCK / select / timeout 等非 POSIX 手段），daemon 主
  循环以分钟为周期，任何阻塞读取都会违反「IPC 超时不阻塞 daemon」。文件通道在
  Android（toybox）与宿主机上行为一致、可逐字节断言，且**等价满足**任务列出的
  「如果使用 FIFO，必须」全部条款：

| 任务「如果使用 FIFO，必须」 | 本实现等价条款 |
| :--- | :--- |
| daemon 创建 | daemon 启动 `ipc_server_init` 创建 `ipc/` 及子目录 |
| 权限 0600 或等价 | `chmod 700`（root-only；比 0600 更严） |
| 请求格式固定 | 单行 `REQ_ID|OP|k1=b64&k2=b64` |
| 请求长度受限 | `IPC_REQ_MAX=4096`（服务端 `wc -c` 校验） |
| 命令白名单 | `IPC_WHITELIST` 12 op + 每 op 参数键白名单 |
| 每请求唯一 ID | `REQ_ID`（客户端生成，服务端校验字符集/长度） |
| 响应文件原子写入 | `ipc_respond` tmp+mv |

### 2.2 控制接口（12 op）

`GET_TASKS` / `GET_TASK_STATUS` / `GET_TASK_LOG` / `VALIDATE_TASK` /
`CREATE_TASK` / `UPDATE_TASK` / `DELETE_TASK` / `ENABLE_TASK` / `DISABLE_TASK` /
`START_TASK` / `STOP_TASK` / `RESTART_TASK`

- 只读/控制（GET_*/START/STOP/RESTART）在 legacy 与 managed 模式均可工作（经
  Registry 快照 + 运行态）。
- **写操作（CREATE/UPDATE/DELETE/ENABLE/DISABLE）仅 Managed 模式**（P3-02
  task-config 权威存储）：legacy 返回 `configuration_invalid`，**config.txt 不
  被 WebUI 触碰**（config.txt 是用户手工权威，行级改写风险大，P3-02 已把
  task-config 立为 canonical Task 存储）。
- START/STOP/RESTART **只接受任务 ID**：命令取自已校验任务文件（Registry 快照
  的 `action.command`），请求里带 `command` 参数 → `invalid_request`（参数键白
  名单拒绝）。这是「不允许 WebUI 传入任意 shell 字符串作为控制指令」的关键。

### 2.3 错误码（可区分，rc）

| rc | error | 触发 |
| :-- | :--- | :--- |
| 0 | ok | 成功 |
| 1 | invalid_request | 格式/未知 op/坏 base64/未知参数键/超长 |
| 2 | permission_denied | 请求目录不可写（未授权路径） |
| 3 | task_not_found | GET/START/STOP/RESTART/UPDATE/DELETE 引用未知 id |
| 4 | configuration_invalid | 写操作在 legacy；VALIDATE 失败；命令缺省/多行 |
| 5 | operation_timeout | 客户端等待超时（daemon 未在期限内响应） |
| 6 | daemon_unavailable | daemon.pid 缺失或指向已死进程 |

## 3. 安全模型（对照验收逐条）

| 验收条款 | 机制 | 测试证据 |
| :--- | :--- | :--- |
| 非法请求不执行任何 Root action | 请求行白名单/字符集/长度/参数键全量校验后才 dispatch；任何失败仅写 invalid_request 响应，绝不调 action_run/tcfg 写 | security a：11 种畸形/注入请求全部 rc=1 且 EXEC_LOG=0、task-config 快照不变 |
| Shell 元字符不进入执行路径 | 值一律 base64（字母表无元字符）；服务端只解码为数据、绝不 eval；START 只取 id | security b：`&command=<b64元字符>` → invalid_request；无 pwn 文件、无 exec |
| 重复请求不重复启动任务 | 同 req_id 响应已存在 → 幂等丢弃；START 已 RUNNING/STARTING → 不重复启动 | security c：同 req_id 重投 exec 保持 1；不同 req_id 但已运行 exec 保持 1 |
| IPC 超时不阻塞 daemon | 服务端逐秒轮询、单轮有界（IPC_POLL_MAX=64）；客户端有界等待 → operation_timeout | security d：70 请求单轮 ≤64 且函数返回；客户端 1s 超时 → rc 5 |
| 未授权路径无法修改 Task | `ipc/` 0700 root-only；请求目录不可写 → permission_denied；非法请求零副作用 | security e：目录 0700；chmod 000 → rc 2；快照不变 |
| daemon 停止返回明确错误 | `ipc/daemon.pid` 存活标记 + `/proc` 检查 | security f：无 pid/死 pid → rc 6 daemon_unavailable |

## 6. 备注与边界

- `su-scheduler ipc <OP> [key=value ...]` 是 IPC 客户端入口（WebUI 后端后续经它
  调 daemon）；`SU_SCHEDULER_IPC_TIMEOUT` 环境变量可调客户端等待上限（默认 5s）。
- daemon 主循环的 nap 段改为「逐秒逼近下一分钟 + 每秒 `ipc_server_poll`」：
  外层 `while true` 仍恰 1 处、调度周期仍以分钟推进（P3-03 锚点不变）。
- 本任务**不实现** WebUI 前端（浏览器页面/本地 HTTP 服务）；交付的是 WebUI 所
  依赖的受控控制平面（协议 + Server/Client + 安全测试），WebUI 界面为后续阶段。
- Dependency/Condition（P4）不在此范围。
