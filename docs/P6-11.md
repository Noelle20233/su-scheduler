## 1. 已修复项（宿主证据；设备复验待重连）

### ① D-P6-10-02（最高优先：孪生 daemon 违反单常驻不变量）
- **根因**：高负载 `cmd_stop` 6s 等待超时后**无条件删锁** → service.sh 看护（C5 禁动）见锁缺失
  noclobber 拉起新实例接管成功，而**旧非持有者进程仍存活**（SIGTERM trap 在负载下被拖慢）→
  双/三 daemon 同 tick（审计每分钟 2–3 行）。既有启动仲裁只在**启动时**判存活者，运行期无二次校验。
- **修复（两文件改动面 + 新原语，择优 a+b 组合）**：
  - **(b) 锁主围栏**（daemon，主改）：`system/bin/su-schedulerd` 主循环 `while true` 顶置
    `lifecycle_lock_owner_fence "$LOCK_FILE" "$$"`（新 §18 原语，`system/bin/su-scheduler-runtime`
    L1449+）：锁内 PID ≠ 自身、且该 PID 存活、且其 `/proc/PID/cmdline` 含 `su-schedulerd`
    → 本实例为接管竞态残留的非持有者 → 记 WARNING + `crash_record_exit 0`（防 crash_seq 假累加）
    + `exit 0`，**绝不删锁**（锁属现任持有者）。保证「任何时刻仅锁持有者执行 tick」——这是直接
    针对测得症状（多行 op=tick）的不变量兜底，且对任意产生孪生的路径（cmd_stop / 重启风暴 /
    noclobber 竞态）都成立。
  - **(a) cmd_stop 删锁门**（CLI）：`system/bin/su-scheduler` L970 `rm -f "$lock_file"` 由无条件
    改为仅在 `gone==1`（全部持有者确认死亡）后删；超时仍有存活实例 → 不删锁 + 打印 `Stop incomplete`
    + `return 1`（交还调用者）。锁保留至旧实例真正退出（其 lock 内 PID 变 stale）后由下一次
    start / 看护安全接管 → 从源头消除「删锁→接管→孪生」。
  - **选择理由**：(b) 是真正的不变量执行者（service.sh 禁动下，令任何 noclobber 接管都收敛为单持有者，
    且直接命中「单 tick 单审计」判据）；(a) 移除 cmd_stop 这一已知孪生制造者、把重叠窗口压到 0。
    二者互补、均为最小 diff，(b) 单独即可将「持续 2–3 行/分钟」收敛为「每 token ≤1 行」。
- **宿主复现**：`tests/lifecycle-prod/test.sh §8`（12 断言）。修复前 `[FAIL] D-P6-10-02 B1: op=tick
  lines=2 (expect 1)`（双实例并存时旧非持有者仍落 tick）；修复后单持有者 tick → 1 行 → PASS。
  A1..A6 围栏语义（holder=hold、活非持有者=yield、死 rival/stale/空锁/非 daemon 持锁=hold 不误伤）；
  C1 daemon 循环顶围栏早于 scheduler_tick、C2 cmd_stop 删锁门、C3 service.sh 零引用围栏、
  C4/C5 原语唯一定义 + selfcheck 注册。
- **文件面**：改 `su-scheduler-runtime`（新原语 + selfcheck）、`su-schedulerd`（循环顶接围栏）、
  `su-scheduler`（cmd_stop 门）。**service.sh 零改动**（其 noclobber 拉起行为原样，由 (a)/(b) 使接管安全）。

### ② D-P6-10-01（僵尸 run 占额饿死新链）
- **根因**：清 `dag/`（连带 `.scanmark`/`.scanpending` 高水位丢失）但留 `cycle-*` 时，
  `dag_scan_registrations` 的扫描窗下界（scanmark）退化为 `-inf` → 历史陈旧 token 被 F2 有界扫描
  重登记为 PENDING run 占满 `DAG_RUNS_MAX=8` 名额 → 新链饿死。
- **修复（§27）**：登记候选（窗口来源 + pending 来源）在登记前加年龄/可解析钳制——新原语
  `dag_token_age_le <tok> <cur> <win>`（纯 awk 历法差 days_from_civil，零依赖/零 wall-clock，
  与 `SCHED_CYCLE_NOW` 冻结时钟一致、跨日/月/年精确）：距当前 token 超窗 / 不可解析 / 未来 token
  → 跳过登记、不回 pending。默认窗 `DAG_SCAN_MAX_AGE_MIN=1440`（24h；可 env 覆盖）。
  - **窗口取 1440 的依据**：合法 pending 补登滞后仅分钟级，而残留来自跨会话/跨日（≥小时~天）；
    24h 窗既不误伤既有有界扫描/高水位测试（`tests/resource/stress.sh` H5 需容忍约 930min 的
    跨日首扫补登，402ms/350ms ≤2000ms 全绿），又拦住陈旧僵尸；测试面 preflight 复位三件套保留（双保险）。
- **宿主复现**：`tests/p6-dag/test.sh §D01`（DAG-D01-01..07）。修复前 `[FAIL] DAG-D01-01 陈旧 cycle
  token 被重登记为僵尸 run` + `DAG-D01-03 新链被陈旧残留饿死（nr run 缺失）`；修复后陈旧跳过、
  新链正常登记 → PASS。D01-04/05 证窗内近期登记不受误伤 + `dag_token_age_le` 原语语义 + 接线/常量的静态守卫。

### ③ D-P6-10-03（kill×respawn 微窗 +1 越钳）
- **根因**：kill -9 落在「节点重试 respawn 已 start、子进程尚未落 exit/未持久化 retry.count」的微窗 →
  恢复把该次判为 `daemon_restart` 残留（**非** `action_failure`）并清 retry 计数 → 旧 `dag_retry_replenish`
  只数 `action_failure` → 少计一次 → `sched_retry_arm` 误判 `count<max` → 多 arm 一次 → `retry.max=1`
  实跑 3 次（1+max+1），且发生在 run 已终局 FAILED 之后。有界非无界。
- **修复（§27，P6-07 F4 边界：不碰 state_sync_one/sched_retry_arm 本体）**：
  - `dag_retry_replenish` 改以 events.log **全部**失败事件（`action_failure`+`daemon_restart`+`timeout`）
    计「已消耗尝试」（不信任残存/已清零的 retry.count，以账本为准）。
  - run 终局分支（`dag_run_update` SUCCESS|FAILED）对 disp+FAILED 成员改调新原语 `dag_retry_terminate`
    （exhaust：`retry.count := retry.max` + 清 `retry.until`）——引擎侧拒绝终局后重放该 run 节点。
- **宿主复现**：`tests/crashguard/test.sh §16 G4`（G1 手法扩展：注入 respawn-start/count-未落盘 的
  daemon_restart 残留 + 清计数）。修复前 `[FAIL] D-P6-10-03 G4 ... cf_ex=3(≤2) attempt1=2 dr=1`
  （正是设备的 1+max+1 越钳）；修复后 cf 总执行 ≤1+max=2、终局后再 4 tick 零重放 → PASS。G4c/G4d
  直测两原语，G4e/G4f 静态守接线。既有崩溃循环测试（G1 b 恰 1+max、R7 lb 总执行 2 经 daemon_restart+retry）
  零回退（无额外失败事件时新旧计数一致）。

  二次构建幂等（无假 dirty），zip 内 docs `su-scheduler chain` 计数 0→**2**。顺带核对：HEAD docs（1341 行）
  较 regen（1548 行）缺失的即 P1-13/P3/P4/P6 各追加章节——属同类漂移，一次性随 README 权威再生收口。
  - `tests/p1-build/build_check.sh` 增断言：zip docs 含 chain、再生含 chain 行、二次 build 幂等；并把
