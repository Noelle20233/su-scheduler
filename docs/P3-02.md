## 2. 设计（双模式配置权威）

| 维度 | Legacy 模式（默认） | Managed 模式（显式导入后） |
| :-- | :-- | :-- |
| 触发 | 无 `task-config/MANAGED` 标记 | 用户通过 WebUI「导入旧任务」或 CLI `task-config import` |
| 权威配置源 | `/sdcard/Documents/su-scheduler/config.txt` | `/data/adb/su-scheduler/task-config/<id>.task` |
| config.txt 角色 | 唯一配置源 | 备份（导入前逐字节）+ 兼容导出 |
| daemon/CLI | 零改动（C2/C4） | 编辑落盘 task-config/；daemon 调度仍走既有执行入口（P3-01 D1） |
| 迁移 | — | 可回滚（`task-config rollback`）、不静默覆盖、重复导入幂等 |

**存储目录**（独立于运行目录 `tasks/`，按任务要求不使用 `tasks/`）：

```
/data/adb/su-scheduler/task-config/
  MANAGED                   标记文件（存在 = managed；**最后写**，中断不产生半管理态）
  manifest                  元数据（mode/source/imported_at/count/backup）
  backup/config.txt.<ts>    导入前逐字节备份（回滚源）
  <id>.task                 每任务一个 POSIX key=value Task v2 文件
```

- 目录可用 `TCFG_DIR` 环境覆盖（测试隔离；生产缺省为上述路径）。
- 命名空间：`tcfg_*`（与既有 `crash_*`/`runtime_*`/`supervisor_*` 前缀隔离，
  不触发 crashguard 等套件的函数计数断言）。

## 3. 任务 ID 兼容与新建规则

| 场景 | ID 规则 | 依据 |
| :-- | :-- | :-- |
| Legacy 导入 | 保留 `t<line>_<trigger>`（如 `t11_boot`、`t35_0915`） | P1-02 §7 + P2-04 idmap 双向解析；旧运行 ID 查询不破坏 |
| Managed 新建 | `task_<trigger_norm>_<n>`（如 `task_weekly10800_1`） | `tcfg_new_id`；`task_` 前缀与 legacy `t<line>_` 命名空间隔离 |
| 删除 / 禁用 / 重命名 | 删除=删文件；禁用=`enabled=0`；重命名=改 `name=`（id 不变，稳定身份） | ADR D5（`docs/architecture/config-authority.md`） |

## 4. 权威与冲突处理（摘录，详见 ADR）

1. **有标记读 task-config，无标记读 config.txt**（`tcfg_mode` 单一判定）。
2. **导入永不改写 config.txt**：只 `cp` 到 backup；任何失败 config 逐字节不变。
3. **重复导入幂等**：已存在 id **跳过**（不产生重复 Task、不覆盖既有条目——
   managed 下用户编辑过的条目不被旧 config 覆盖）。
4. **冲突**（legacy 与 v2 同时存在内容不同）：以 MANAGED 标记判定权威；managed
   下 task-config 为准，config.txt 是备份/导出；legacy 下 config.txt 为准，
   task-config 惰性（存在但不用）。
5. **写失败回滚**：全写经 tmp+mv 原子；导入 staging 失败即清理、不写 MANAGED；
   `tcfg_rollback` 恢复备份 config + 移除标记回到 legacy。
6. **旧用户不打开 WebUI**：无标记 → 纯 legacy，零行为变化。

## 5. Legacy 导入与备份流程（可验证）

```
task-config import <config>
 ① 校验 config 存在（缺失 → rc=2，无任何写）
 ② 逐字节备份 config → backup/config.txt.<ts>（cp；config 本身不改）
 ③ 解析 config → staging（legacy_adapter_parse；C2 原样复用）
 ④ 逐文件校验（schema_version=2 / id==文件名 / trigger 非空）
    0 有效任务（损坏/全注释）→ 清理 staging，rc=1（config 逐字节不变）
 ⑤ 幂等提升：已存在 id 跳过，新 id 经 tmp+mv 原子落盘
 ⑥ 写 manifest + MANAGED 标记（**最后写**：中断不产生半管理态）
```

**备份**：`backup/config.txt.<ts>` 是导入前 config.txt 的逐字节拷贝——既是
回滚源，也是「不允许静默覆盖用户配置」的兜底。

**回滚**：`task-config rollback <config>` → 找到最新备份 `cp` 回 config（逐字节
还原）→ `rm MANAGED` → 回到 legacy；task-config 文件保留为惰性（不误删用户
数据）。

**导出**：`task-config export <out>` → 逐任务反向生成兼容 legacy 行
（`<trigger> <action.command>; : <flags>`，schema §8.4；块任务输出重构行——
兼容导出而非逐字节还原）；跳过非法任务文件。
