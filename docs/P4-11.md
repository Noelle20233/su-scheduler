## 3. 真机缺陷修复记录（P4-11 发现，全部有先失败后通过证据）

> 三处缺陷都是 **Runtime 1.28.0 在真机首次激活后暴露的既有兼容问题**（P3/P4 开发期
> 无真机可验）。每个缺陷均已在宿主加回归断言（p4-dependency 219 断言 / cli 29
> 断言），修复后全量回归全绿 + 真机冒烟全绿。

### D-A：mksh `(`-in-pattern 参数展开（Runtime 库 source 失败）

- **现象**：P4-06 Condition 引擎 `cond_grammar_ok`/`cond_eval` 使用
  `${conde_l#task.state(}` / `${conde_id%)}` 这种 **pattern 含裸 `(`/`)`** 的参数
  展开。设备 `/system/bin/sh`（mksh R59，Android 16）**无法解析**（`no closing
  quote`），整个 Runtime 库（5622 行）source 失败 → daemon 降级 legacy 模式，
  P4 全功能（依赖/Condition/Registry/IPC/WebUI）在真机不可用。
- **根因**：与 P3-10 D-IPC（`|`-in-pattern）同源——mksh 对 pattern 内裸特殊
  字符解析缺陷；bash/dash 正常，故宿主测试无法发现。
- **修复**：4 处（`cond_grammar_ok` ×2、`cond_eval` ×2）改为可移植
  `cut -d'(' -f2 | cut -d')' -f1`（P3-10 D-IPC 同款手法，零语义变化）。
- **回归**：p4-dependency 新增 §P4-11 mksh 静态断言（生产库零裸
  `(`/`)`-in-pattern）；真机 `sh -n` 通过 + `cond_grammar_ok` 实测正常。
- **提交**：`[P4-11] fix`（与 D-B/D-C 同 commit，5 files / +131 -17）。

### D-B：`cmd_stop`/`cmd_status` 依赖 `pidof su-schedulerd`（Android 进程名不匹配）

- **现象**：daemon 是 shebang 脚本，Android 上进程名显示为 `sh`，`pidof
  su-schedulerd` 返回空 → `cmd_stop`/`cmd_status` 无法定位 daemon → restart 时
  **杀不掉 service.sh watchdog 拉起的其他实例** → 多实例并存竞争写
  `daemon.guard` → crash_seq 累积 → crash-guard **degraded（300s 快速退出循环）**
  → 时间任务/IPC 全部中断（p1-device 时间任务、p3-device 7/8/14 反复
  `operation_timeout`）。
- **修复**：新增 `daemon_pids()` 按 `/proc/*/cmdline` 匹配全部 `su-schedulerd`
  实例；`cmd_status` 用之判 Alive、`cmd_stop` 用之 **kill 全部实例并等待退出
  后再删 lock**（消除 watchdog 竞态窗口）。
- **回归**：cli 测试新增 mock 双进程断言（daemon_pids 全捕获 + cmd_stop 全杀 +
  cmd_status Alive）；真机 restart 后单实例、crash_seq 归零。

### D-C：daemon 单实例保护等待后强制接管（双实例竞态）

- **现象**：既有单实例保护在 lock 存活时**等待 5s 后强制接管**（rm lock 继续
  启动）→ `su-scheduler restart` 与 service.sh watchdog 同时拉起两个实例
  （实测 restart 后双 PID 几乎同时 initialized）→ 双实例竞争 IPC 目录 → 请求
  无响应。
- **修复**：等待 5s 后旧实例**仍存活 → 本实例退出**（strict single-instance，
  `refusing to start`），仅 stale lock（PID 已死）允许接管。
- **回归**：cli 测试新增静态断言（daemon 含 `LOCK_STILL_ACTIVE` / `cmd_stop`
  等待退出）；真机 restart 后严格单实例。
