## 3. 复现断言（Part C/D/E — 当前代码上应当 FAIL）

全部位于 `tests/p6-reliability/test.sh`。三个 O-断言在**当前生产代码**上稳定 `[FAIL]`（各跑 2 次确认，见 §6），证明缺陷存在、可复现。

### O-2 — 主循环跳拍（精确 HHMM 任务被跳过，不补执行）

- 触发命令（含于 test.sh §O-2 段落）：
  ```bash
  SCHED_CYCLE_NOW=202609060829 scheduler_tick "$O2_T/base" "$O2_T/config.txt" "$O2_T/tasks" "0829"
  SCHED_CYCLE_NOW=202609060831 scheduler_tick "$O2_T/base" "$O2_T/config.txt" "$O2_T/tasks" "0831"
  ```
- 背景：`scheduler_tick`（runtime `~4114`）每次以当前 HHMM 作为 `now`，仅执行 `now`
  命中的精确时间任务；**无「上次 tick」追踪**。单次循环跨越 >60s（0830→0831）时，
  0830 窗口的精确任务被跳过且不补执行。
- 断言：0830 任务在 0831 tick 应被**补执行**（catch-up）。当前实现 `now=0831` 与
  `trigger=0830` 不匹配 → 不执行 → 断言 **FAIL**（缺陷已复现）。
- 对应代码：`scheduler_tick`（runtime `4114-4165`）内 `sched_execute_one` 仅当
  `trigger_decide` 返回 `due=Y` 才执行（`4023-4033`）；`time` 族匹配见 `1960-1966`。

### O-3 — Cron trigger 含空格时 ID 派生非法路径字符

- 触发命令：`tcfg_new_id "cron:0 8 * * *"`
- 背景：`tcfg_new_id`（runtime `~3219`）实现为 `norm=$(echo "$trig" | sed 's/://g')`，
  只去冒号**不去空格** → `cron:0 8 * * *` 派生 `task_cron0 8 * * *_1`（含空格/`*`），
  作为文件路径断裂/非法。
- 断言：返回 ID 必须满足现有路径字符集 `[A-Za-z0-9._-]`（无空格/`*`/`/`），且同输入
  同 ID（可复现）。当前返回 `task_cron0 8 * * *_1` → 断言 **FAIL**（缺陷已复现）。
- 对应代码：`tcfg_new_id`（runtime `3219-3227`）。合法 ID 字符集参照
  `tcfg_new_task` 的 id 校验（`3414-3416`）。

### O-4 — IPC VALIDATE_TASK 错误详情丢失

- 触发命令（test.sh §O-4 段落）：
  ```bash
  ipc_op_validate "$O4_T/base" "v_nocmd"   "trigger=$(ipc_b64enc '09:00')"
  ipc_op_validate "$O4_T/base" "v_badtrig" "payload=$(ipc_b64enc "$BAD_PAYLOAD")"
  ```
  其中 `BAD_PAYLOAD` 含 trigger `oneshot:2460`（非法）。
- 背景：VALIDATE_TASK 的 payload 通道（P3-06）经 `tcfg_editor_validate_payload`
  全字段校验失败时，仅回笼统 `configuration_invalid "task invalid"`
  （runtime `4386-4395`），**不透传具体字段与校验原因**（缺哪个字段 / 哪个字段非法）。
- 断言：trigger-非法（`oneshot:2460`）的错误信息应能区分字段/原因（≠ 笼统
  `"task invalid"`，且与「缺 command → trigger+command required」不同）。
  当前 trigger-非法仅回 `"task invalid"` → 断言 **FAIL**（缺陷已复现）。
- 对应代码：`ipc_op_validate`（runtime `4386-4423`）。
- 备注（O-4 记录，P6-04 深入）：payload 存在「双 Base64」编码层级问题（`payload` 参数
  本身 base64 编码的完整 task 文本，其内字段不再逐字段编码），本套件仅在纯函数级断言
  「错误原因不具体/无字段区分」，编码层级问题留 P6-04 处理。

## 7. 与背景描述不符之处 / 实际采用的替代方案

1. **O-4 复现通道调整**：背景建议走 `trigger+command` 通道提交字段级非法 payload。但
   `ipc_op_validate` 的 `trigger`+`command` 通道所构造的 sandbox 任务（runtime
   `4404-4415`）仅做 `tcfg_validate_task`，其只校验 schema/id/trigger 非空/dependency
   /condition（`3188-3208`），**不校验 trigger 格式**；非法 trigger（如 `oneshot:2460`）
   在该通道会**通过**校验返回 `valid`，无法触发 `"task invalid"`。故 O-4 改用 **payload
   通道**（P3-06，经 `tcfg_editor_validate_payload` 全字段校验），对非法 trigger 稳定
   复现笼统 `"task invalid"`。
2. **`parse_modifiers`/`extract_command` 位置**：二者定义于 **`su-schedulerd`**（`522-573`，
   非 runtime），且依赖 `local`（bash 语法）。按 legacy/golden 的 derive 手法从 daemon
   切出后 source 使用（tests/p6-reliability/test.sh §compat）。
3. **性能基线改为测「决策」而非「执行」**：初始版本在 0830 tick 使 50 个 08:30 任务全部
   执行，`action_run` shim 子进程开销使 full≈10s，超过宽松上界。改为 tick 在 09:00
   （永不命中、零执行）+ 首 tick 预热，得到纯决策基线（full≈1731ms），符合「记录性
   基线」定位。
4. **`PERF_TASKS_DIR` 遗漏**：首个实现漏定义该变量，`set -u` 下 perf 子 shell 直接退出；
   已补定义。
