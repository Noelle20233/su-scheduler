# P6-04 — IPC 错误原因透传（configuration_invalid 字段级诊断）

> 阶段：P6（可靠性）；任务：P6-04 — 类型：修复（最小改动）。

## 1. 缺陷（O-4）与根因

`ipc_respond <base> <rid> <op> <rc> <ERROR> [载荷]` 的既有调用约定把**符号名**
（`configuration_invalid` / `invalid_request` / `ok`）放在第 5 参（响应首行第 4 段
= ERROR 字段），把**具体诊断文本**放在第 6 参（响应第 2 行载荷）。校验失败时：

- `tcfg_editor_validate_payload` / `tcfg_apply_task` 写到 stderr 的字段级诊断
  （如 `trigger 'oneshot:2460' invalid/unsupported ...`）被**直接丢弃**
  （stderr 流向 daemon 日志），ERROR 字段只剩笼统符号；
- CLI 消费端（`task_ctl_send` 等）与 WebUI Reader（`cmd_webui`）都只读首行
  第 4 段（`cut -d'|' -f4`），错误响应时载荷行被丢弃 → 用户/前端拿不到
  「哪个字段、为何非法」；
- §O-4 复现：「缺 command」与「trigger 非法」的 ERROR 字段完全相同
  （均为 `configuration_invalid`）→ 不可区分。

## 2. 错误链审计（编码层级，要求 5）

审计对象：请求 → 服务端 → 响应 → CLI → WebUI 全链的编码层级。

| 环节 | 位置 | 编码 | 结论 |
| :--- | :--- | :--- | :--- |
| 请求构造 | CLI `task_ctl_send`/`cmd_ipc`/`cmd_webui`（`su-scheduler` L1246/1435/1469） | 每参数 `ipc_b64enc` 一次（`k=b64&k=b64`） | 单层 |
| 请求解析 | `ipc_parse`/`ipc_params_valid`（runtime L4403/4426） | 格式校验，不解码 | — |
| 参数取值 | `ipc_param` → `ipc_b64dec`（runtime L4440） | **解码一次**得明文 | 单层 |
| 响应写入 | `ipc_respond`（runtime L4443） | ERROR 字段**明文** printf；仅载荷（成功数据）按需 b64 | 明文 |
| 响应读取 | `ipc_client_send`（runtime L4856） | `cat` 原样回传，零转换 | 明文 |
| CLI 消费 | `task_ctl_send`/`cmd_ipc`（`su-scheduler` L1253/1440） | `cut -f4` 原样输出 stderr（明文） | 明文 |
| WebUI 消费 | `cmd_webui` 错误 JSON（`su-scheduler` L1480） | `web_json_str`（= `web_json_escape`）转义进 JSON 字符串 | 转义点 |

**结论：全链不存在双 Base64 实点**——base64 只存在于「请求参数值」与
「GET_TASK_EDIT/编辑器数据载荷」两处单层编码；ERROR/reason 全程明文，WebUI
侧唯一再编码是 JSON 字符串转义（非 b64）。因此本任务**只成文审计结论，无需
改动编码**；唯一发现的真实缺口是 `cmd_webui` 此前用 `%s` 手工拼引号
（`"error":"$err"`），新 reason 可含 `"`/`\` → 破坏 JSON ——已改经
**既有** `web_json_str` 转义（复用 P3-05 函数，未新造转义器）。前端
`webroot/app.js` 对 `error` 一律经 `escText` 渲染，唯一精确比较
`=== "task_not_found"` 的分支（L353）所依赖的 task_not_found 字段本任务**未
改动**（仍为纯符号），兼容。

## 3. reason 构造与净化管线（要求 2/3/4）

### 3.1 捕获（校验器 stderr → 响应 ERROR）

- payload 通道（`ipc_op_validate`）：`tcfg_editor_validate_payload "$pl" 2>"$base/ipc/.valerr.$$_p"`；
- EDIT_TASK（`ipc_op_edit_task`）：`tcfg_apply_task "$id" "$payload" 2>"$base/ipc/.valerr.$$_e"`
  （含其内部 editor 校验与 `payload id mismatch` 诊断）；
- 文件通道（validate sandbox / create sandbox / update 后校验）：
  `tcfg_validate_task` 本身零 stderr（只有 0/1），新增**纯只读**诊断函数
  `tcfg_validate_reason <file>`（runtime L3213）按 `tcfg_validate_task` 相同
  判定顺序（文件存在→schema_version→id 一致性→trigger 非空→dependency→
  condition 语法→condition 文法）输出**首个失败点的字段级原因**；
  不改 `tcfg_validate_task` 本体、不改其判定结果（C2/C4）；
- 既有具体字符串（`trigger+command required`、`command must be single-line`、
  `write ops require managed task-config ...`、`missing id`、`write failed` 等）
  原样作为 reason 保留，并**同时**写进 ERROR 字段（`符号: 原因`）与载荷行
  （第 6 参不动）→ 任何读取载荷行的旧消费者零破坏。

### 3.2 净化（`ipc_err_sanitize`，`ipc_respond` 唯一写入咽喉，L4344）

单次 awk 进程完成（POSIX awk，dash/mksh/gawk/mawk/toybox 兼容）：

```
捕获文本 ─→ 取首个非空行（多行 stderr 不再可能产生伪载荷/换行）
        ─→ 非可打印 ASCII（含 \n/\r/\t 与控制符）→ 空格；`|` → `/`
        ─→ 剔除 `[editor] ERROR:` / `[task-config] ERROR:` 等前缀，折叠空格
        ─→ 脱敏：daemon base 具体值 → `<path>`；TCFG_DIR 具体值 → `<path>`
           （awk index() 字面匹配，防正则元字符逃逸）；
           `/data/adb[A-Za-z0-9._/-]*` 字面量 → `<path>`
        ─→ 去尾部空白/冒号（reason 为空时优雅回退为纯符号 = 旧行为）
        ─→ 长度 > IPC_ERR_MAX(256) → 截断至 242 + "...(truncated)"（恒 ≤256）
```

净化位于 `ipc_respond` 咽喉点 ⇒ **所有** 服务端响应（含未来新代码）的 ERROR
字段协议安全恒成立；第 1/2/3 段（rid 白名单校验/op 白名单/数字 rc）产生点不
变，响应行格式不变（仅第 4 段内容更具体）。

## 8. run_tests.sh 注册评估（任务书可选项）

**暂不注册 `tests/p6-reliability`**，理由：套件 §perf 对 50 任务
`scheduler_tick` 设 2000ms 宽松上界，本机（WSL 原生 ext4）实测已
1738–1847ms，接近阈值——注册进 CI（ubuntu-latest 共享 runner）存在**超界
误红**风险，连带阻断 `run_tests.sh` 门禁。P6-01/02/03 亦均未注册。建议
P6-05 出口评审时结合 CI 实测数据决定（或届时将上界放宽为记录性输出）。
本任务已验证：注册后全量 49 套件 `EXIT=0` 全绿（WSL 本机，含该套件）。

## 9. 登记未修事项（本任务范围外，回队长/P6-05 裁决）

1. `ipc_server_poll` 对 malformed 响应的 REQ_ID 段取自请求**文件名**
   （`basename` 后未再过 `[A-Za-z0-9._-]` 门），文件名含 `|` 时可污染响应首行
   段数。利用前提已是可向 0700 root 目录写文件（等价于已失陷）；ERROR 字段
   本身已由 §3.2 咽喉净化，伪响应面显著收窄。建议 P6-05 评估对 rid 段同样
   过 `ipc_err_sanitize` 或白名单。
2. `ipc_op_update` 校验失败时（`invalid after update`），先前 `tcfg_set_field`
   的字段改动**已落盘不回滚**（既有行为，本任务仅追加诊断文本，未改此语义）。
3. `ipc_op_set_enabled/start/stop/restart/check` 的 `configuration_invalid`
   详情仍只在载荷行（tctl 层已有具体消息，非「校验器 stderr 丢弃」缺陷面）。
